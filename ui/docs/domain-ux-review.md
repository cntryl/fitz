# Domain UI/UX Review and Plan

Audit date: 2026-10-03. Status: UI changes implemented across all seven domains; scoped API-contract and broker-backed validation remain open.

## Audit scope and evidence

The review covered KV, Queue, Stream, Lease, Notice, RPC, and Schedule at the domain root, realm, area, and resource tiers, plus the Notice, RPC, and Schedule operation tiers: 31 page shapes. It also opened KV rows, Queue messages, and Stream records on demand. The Queue `acme/payments/orders` resource was the starting point.

The page walk used the local mock UI in Route Family 2. Source review covered page owners, UI mappers, inventory aggregation, generated API contracts, admin projections, family statistics, and diagnostic rules. Mock screens establish layout and interaction findings; they do not establish current broker health or production aggregation correctness. No replay, purge, or schedule execution was performed.

This plan supersedes the earlier requirement for a summary strip at every hierarchy tier. It also corrects the earlier suggestion to use API diagnostic severity directly as domain health: those diagnoses need a scope and semantics review first.

## Implementation outcome

The shared hierarchy cleanup and the KV, Queue, RPC, Lease, Stream, Notice, and Schedule detail layouts are implemented. Default domain pages now lead with comparison tables and scoped evidence, omit inventory hero totals and prose summaries, and distinguish missing health coverage from measured activity. Inspection remains on demand where it expands bounded or detailed data.

The UI maps only fields already present in the generated API contracts. No backend health rules or new scoped measurements were introduced. The family stats, diagnostic semantics, scoped measurement attribution, and production broker checks listed below still require separate contract work before the UI can make stronger health claims.

## Design decisions

1. Remove the default prose summary blocks, including domain descriptions, paragraphs interpreting the current totals, and repeated durability explanations. Put necessary field definitions beside their evidence or in an optional disclosure.
2. Remove cards containing a single statistic. Use tables, compact definition lists, and small inline groups of related facts. A table should not acquire a row of cards repeating its totals.
3. Remove area, resource, operation, stream, and similar inventory totals from the page's prominent content. Counts remain useful for filtered results, pagination, truncation, or an explicit capacity decision.
4. Make each prominent signal answer an operator question: what needs attention, where it is, how long it has been happening, and what evidence or action is available.
5. Let child tables carry comparison at the root, realm, and area tiers. Add a scope-level measurement only when it supports a decision that the table cannot communicate directly. Do not replace every summary strip with a compressed version of the same strip.
6. Keep activity, health, freshness, and coverage distinct. An active transaction, subscriber, owner, append session, or enabled schedule is normal activity. A refreshing query must not hide a previously observed issue.
7. Preserve route search, sortable useful columns, row navigation, breadcrumbs, refresh, and on-demand data access. Preserve existing action confirmations and results.

### Page contract

| Tier        | Operator decision                                                  | Default content                                                                                                                                        |
| ----------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Domain root | Which part of this Route Family needs inspection?                  | Route identity, compact evidence-based status when available, freshness, realm comparison table. A real issue links to the affected scope or resource. |
| Realm       | Which area is responsible for the observed condition?              | Scoped identity and area comparison table. No area/resource totals or repeated table aggregates.                                                       |
| Area        | Which resource needs intervention?                                 | Scoped identity and resource comparison table, sortable by the same signal that prompted the drilldown.                                                |
| Resource    | What is happening here, and what should I inspect or do?           | A few related operational facts, evidence rows, filters, and domain-specific actions. Secondary measurements are optional.                             |
| Operation   | What is happening on this route, and what outcome can I establish? | Exact-route evidence, relevant definition or registrations, and available actions. Notice patterns require their own honest identity.                  |

The visual order is breadcrumbs, route heading and available actions, compact status/freshness/coverage, then the main table or evidence. There is no required summary component between the heading and the work surface.

Use the existing `DomainDrilldownTable` and its scope/resource/operation adapters for hierarchy navigation. Keep the `Route` column and fully qualified route identity. `realm` remains an application-defined namespace; it is independent of the Route Family selected in the URL.

### Health contract

- Show an issue only with scoped evidence, a meaningful condition, and a drilldown destination. Show the measured value alongside it.
- Do not infer `Growing`, `Stalled`, or recovery from a single count. A trend requires comparable samples and a stated window.
- Reserve a healthy assessment for checks with known coverage and valid measurements. If the page has only activity measurements, show those measurements and the health coverage as unavailable.
- Missing, unmeasured, stale, partially observed, and measured zero are different states. Use a compact label or `—` with an accessible explanation; do not substitute zero for absent data.
- Keep threshold judgments tied to documented broker semantics or an explicitly configured expectation. Do not invent a universal latency SLO, subscriber requirement, or maximum ownership age.
- Broader history and diagnostic reasoning belong in an optional evidence disclosure. They are not another prose summary at the top of the page.

### KV

Owners: [KV overview](../src/pages/app/kv.tsx), [KV resource](../src/pages/app/kv-resource.tsx), [row sections](../src/features/kv/kv-resource-sections.tsx).

| Page     | Decision and primary evidence                                                        | Prune or demote                                                                                                                             | Planned change                                                                                                                                                                                                                                            |
| -------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Root     | Locate resources with transaction activity or elevated reported read/write latency.  | Key totals, operations rate without a valid family measurement, three stat cards, and the unsupported claim that KV has no pressure signal. | Use realm rows to locate activity and latency. Do not equate `Active` with health.                                                                                                                                                                        |
| Realm    | Compare areas by active transactions and worst reported resource read/write p95.     | Areas/resources totals and repeated aggregate values.                                                                                       | Keep the area table; records and storage become secondary columns.                                                                                                                                                                                        |
| Area     | Compare resources by the same transaction and latency signals.                       | Resource total and aggregate strip.                                                                                                         | Keep the resource table and sort by the value being investigated.                                                                                                                                                                                         |
| Resource | Inspect authoritative values, ongoing transactions, and reported read/write latency. | Any inventory-scale hero totals.                                                                                                            | Fetch the existing resource detail alongside the lookup/rows workflow. Link active transactions to an on-demand transaction table with mode, start time, idle time, and operations. Keep exact key lookup, encoding, prefix, limit, copy, and pagination. |

KV read/write p95 comes from the last 256 retained samples for that resource, not a fixed time window. Telemetry retains at most 128 resources and can evict a resource's samples. Label parent aggregates **Worst reported read p95** and **Worst reported write p95**; these are maxima of resource percentiles, not a percentile across the whole scope. Estimates and missing latency remain visibly distinguishable from complete measurements.

An open transaction is not proof of contention. A useful contention assessment needs actual wait/conflict/failure evidence with appropriate scope; the current family commit-failure counters cannot provide it.

| Area     | Identify the queue requiring inspection.                                                                 | Resource total and duplicated summary strip.                                                          | Use the resource table with the same actionable columns. | Resource | Decide whether work is progressing, reservations need inspection, or dead letters need intervention.     | Independent stat cards, subscription count as worker availability, and automatic timeline prominence. | Use compact backlog/progress facts: ready, oldest ready age, delayed, in flight, dead-lettered, and enqueue/completion rates when measured. The existing resource detail already has `oldest_message_age_seconds`, which the actor derives from **ready** messages. Use it as **Oldest ready**. `oldest_backlog_age_seconds` and backlog age buckets include delayed messages and time since initial enqueue; an intentionally delayed message must not become a worker-starvation alarm.

Reservation rows should expose attempts, expiry/remaining time, and the relevant session or owner evidence. Dead-letter rows should expose reason, attempts, and time before replay/purge. Preserve action confirmations and readback. Loaded row counts describe the returned page, not a second authoritative backlog total.

Reconcile the earlier Queue layout edits with this plan: the two large summary groups and restored prose header content are not the desired final pattern.

| Page     | Decision and primary evidence                                                           | Prune or demote                                                                                                   | Planned change                                                                                                                                                      |

| Root     | Locate measured commit/projection failures or inspect durable history.                  | Total stream/event cards, prose about subscriber catch-up, and the existing subscriber-lag health interpretation. | Use realm comparison and actual attributable issues when available. State consumer progress as unavailable.                                                         |
| Realm    | Identify an area with observed broker commit/projection trouble or inspect its history. | Areas/resources totals, duplicated committed/storage aggregates.                                                  | Keep the area table; committed volume and storage are secondary scale information. | Area     | Locate the affected concrete stream.                                                    | Resource count and duplicate rollups.                                                                             | Keep resource rows with the committed read boundary and any valid scoped issue signal. Committed watermarks bound readable durable history. They do not report a subscriber's replay cursor. The existing watermark-lag buckets compare committed area watermarks within a realm/area; they do not measure subscriber consumption. Remove the current subscriber-catch-up wording and its arbitrary threshold.

The current resource projection commonly reports the same committed value for offset and watermark. Do not manufacture consumer lag from their difference. Any future commit-boundary gap needs an agreed meaning before it becomes a health signal. Consumer replay health requires a separate consumer-position contract; it is not available from today's fields.

Treat active ownership as normal activity.                                                                                                       |
| Realm    | Find the area containing waiting or ownership evidence.                           | Areas/resources totals and repeated aggregates.                               | Prioritize waiter columns; keep active ownership as context and ownership age secondary.                                                                                                        |

### Notice

| Page              | Decision and primary evidence                                                              | Prune or demote                                                                                                | Planned change                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Root              | Locate live registrations/activity and attributable delivery drops or rejects if measured. | Subscriber/rate/delivery cards and prose claiming subscribers are receiving fanout from their existence alone. | Compare realms by live subscriptions and a correctly scoped publish rate. Keep unmeasured delivery health unavailable.                                                                          |
| Realm             | Identify which area has the registrations/activity being investigated.                     | Areas/resources totals and cumulative delivered aggregates.                                                    | Use the area table with subscriptions and recent publish rate; move lifetime receipt counts to supporting evidence.                                                                             |
| Area              | Locate the concrete resource or observed pattern.                                          | Resource total, duplicate totals, and cumulative receipts as a primary health measure.                         | Use resource rows with the same live activity columns and honest observation coverage.                                                                                                          |
| Resource          | Inspect which observed subscriptions/patterns are registered and publishing.               | Operations/subscribers/publish-sum cards over a capped observation list.                                       | Make the observed route/pattern table the work surface. Keep coverage/cap indication beside it.                                                                                                 |
| Operation/pattern | Inspect matching subscriptions and route-level publish evidence.                           | Repeated route publish totals on every subscription and lifetime counters as prominent stats.                  | Show route-level rate once, then subscription/session/state evidence. Keep per-subscription receipt counts as supporting data. Correct the row identity, link target, and query scope together. |

`Delivered` currently represents notifications received over a live subscription's lifetime, not an application processing acknowledgement. Resource publish rate is a recent one-minute measure; the broker-wide overview rate instead uses Notice requests divided by uptime, and the family field is unmeasured. These are not interchangeable rates.

There is no complete Notice operation registry. Resource rows derive from bounded live observations. The mapper currently treats a full subscription pattern URI as an operation name, then encodes it again into the operation URL. Patterns can be wildcard subscriptions, so simply stripping the URI prefix does not establish an exact operation inventory. The design and contract must distinguish a concrete operation from an observed subscription pattern.

An empty subscription set can be intentional. Assert missing receivers only against an explicit application expectation. Notice remains live ephemeral fanout; observations do not establish replay or durable delivery.

Wildcard worker registrations can match multiple operations. Do not sum these counts into unique workers or infer capacity from them. Preserve nullable exact-route handled counts and latency attribution; missing does not mean zero calls handled. RPC evidence is live and bounded, not durable request history.

## Acceptance criteria

- No default prose summary blocks, single-stat cards, or area/resource/operation inventory hero totals.
- Root, realm, and area pages use child tables for comparison; the signal that raises an issue remains visible down to the affected resource or operation.
- Each primary field supports a documented operator decision. Secondary scale/history measurements do not crowd out the evidence and actions.
- Normal activity is not automatically a problem. Delayed Queue work, active KV transactions, lease renewals, live subscribers, and historical counters do not manufacture pressure or trends.
- Measured zero, unknown, missing, stale, partial, and estimated values remain distinguishable. Refresh status does not replace issue state.
- Rates, percentiles, maxima, lifetime counters, wildcard matches, and bounded observations have accurate scope/window/coverage labels. Necessary explanations are contextual or disclosed.
- Notice pattern identity and operation URLs are consistent. RPC worker coverage is route-matched. Stream watermarks do not imply consumer progress. Schedule handoffs do not imply downstream completion.
- KV lookup/rows, Stream replay queries, Queue inspection/replay/purge, and Schedule Run now keep their existing safeguards and outcomes. Data inspection remains on demand.
- No per-resource detail fanout is added to make parent summaries look complete. Scoped APIs are used for new parent measurements.
- Review every page shape on desktop and mobile, in light and dark themes, with calm activity, real pressure, idle, stale/error, missing, partial, and wildcard scenarios. Use focused behavior tests for availability, route identity, aggregation, and action outcomes when implementing.
