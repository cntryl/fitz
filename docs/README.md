## Documentation layout and purpose

This folder is the canonical place for project documentation. The goal of this README is to act as a short table of contents and to explain what belongs where so contributors know where to add or look for information.

High-level directories (under `docs/`):

- `docs/dev/` — Developer-level guidance and conventions. These documents explain how the code should be written, how to set up a development environment, testing and linting guidance, CI expectations, and other code-quality topics.
- `docs/features/` — Polished feature documentation. Each feature should have a finalized, user-facing (or developer-facing) summary that explains what the feature does, why it exists, how it works at a high-level, and any acceptance criteria or requirements. These are NOT WIP notes — they describe the final product.
- `docs/wip/` — Working notes, design sketches, partial specs and explorations. Use this as a scratch pad while developing features. As work completes, mature docs should be moved into `docs/features/` (or deleted if no longer relevant).

## How to use these docs

- Read `docs/dev/*` when you need to understand coding styles, repo conventions, or how to run and test the project locally.
- Read `docs/features/*` when implementing, reviewing, or using a finished feature; these pages should be concise and stable.
- Use `docs/wip/*` while a feature is under active design or investigation. Move the doc to `docs/features/` when the design stabilizes and is ready to be referenced by others.

## Authoring guidance

- When creating or updating docs, prefer short, focused files. Use headings, bullets, and examples.
- If a document documents *how to work* (process, tools, code style) put it in `docs/dev/`.
- If a document documents *what the product does* and *how to use it*, or is a spec for a finished feature, put it in `docs/features/`.
- If a document is a partial design, notes, or experiments, put it in `docs/wip/`.

### File naming and front-matter (optional)

- Use lowercase hyphen-separated names, e.g. `how-to-run.md`, `notice-spec.md`.
- If/when we adopt a static site generator, keep titles and short metadata on top of files in a lightweight front-matter block (YAML or TOML). For now, keep files plain markdown unless metadata is required.

## Suggested minimal template

For `docs/features/<feature>.md` or a finalized doc, consider this structure:

1. Title (top-level heading)
2. One-paragraph summary (what and why)
3. Requirements / acceptance criteria
4. High-level design or behavior
5. Runtime/configuration notes
6. Links to code, tests, and related docs

For `docs/dev/*` (guides, checklists), prefer short, actionable steps followed by examples/commands.

## Example workflow

1. Draft design in `docs/wip/<feature>-notes.md` while iterating.
2. Once stable, create `docs/features/<feature>.md` with the polished summary and move or rework the notes as an appendix or remove them.
3. If the feature requires changes to developer workflows, update `docs/dev/*` accordingly.

## Where to put what — quick reference

- Coding conventions, linters, build/development setup: `docs/dev/`
- Finalized feature docs and user-facing descriptions: `docs/features/`
- Work-in-progress designs, partial specs, investigations: `docs/wip/`

## Contributors

If you're unsure where a doc should live, open a short PR and add a brief rationale in the PR description. Keep docs focused and move long-running design conversations to issues where appropriate.
